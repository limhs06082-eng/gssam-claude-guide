## 무엇을 만드나요

이번에는 만들 것을 제가 정해 드리지 않습니다. 여러분이 정합니다.

지금까지 아홉 개의 프로젝트에서 판단 순서를 반복했습니다. 저장이 필요한가, 여러 기기인가, 여러 사람인가, 실시간인가, 로그인인가, 역할이 다른가. 이제 그 순서를 스스로 적용해 봅니다.

주제는 지금 나를 번거롭게 하는 일에서 찾는 것이 가장 좋습니다. 매주 반복해서 손으로 하는 일, 종이로 관리하다 자꾸 잃어버리는 것, 여러 사람에게 같은 내용을 매번 다시 안내하는 일 같은 것입니다.

## 생각하기

종이를 한 장 꺼내 아래 여섯 질문에 순서대로 답하세요. 중간에 답이 정해지면 나머지는 "아니요"로 두면 됩니다.

<Steps>
<Step title="데이터를 저장해야 합니까?">
매번 새로 시작해도 되는 도구라면 아니요입니다. 저장 기능 없이 만듭니다. 여기서 끝나면 가장 빨리 완성됩니다.
</Step>
<Step title="현재 기기에서만 써도 됩니까?">
예라면 [LocalStorage](/storage/what-is-localstorage)로 충분합니다. 다른 컴퓨터나 휴대폰에서도 같은 내용을 봐야 한다면 아니요입니다.
</Step>
<Step title="여러 사람이 같은 데이터를 봐야 합니까?">
예라면 [데이터베이스](/database/what-is-a-database)가 필요합니다. 각자 자기 것만 쓰는 앱이라면 아니요입니다.
</Step>
<Step title="변경 내용이 바로바로 보여야 합니까?">
같은 시간에 함께 보는 화면이라면 예입니다. 각자 다른 시간에 열어 본다면 아니요입니다. [실시간 기능이 필요 없는 경우](/realtime/when-not-to-use-realtime)를 먼저 읽어 보세요.
</Step>
<Step title="사용자를 구분해야 합니까?">
사람마다 다른 내용이 보여야 한다면 예입니다. 이때 [로그인](/auth/why-login)이 필요합니다.
</Step>
<Step title="사용자마다 할 수 있는 일이 다릅니까?">
누구는 만들고 누구는 보기만 한다면 예입니다. 이때 [권한 관리](/auth/what-is-authorization)가 필요합니다.
</Step>
</Steps>

답을 다 적었으면 표로 옮겨 적으세요. 이 표가 그대로 요청의 재료가 됩니다.

| 질문 | 내 답 |
| --- | --- |
| 데이터를 저장해야 합니까? | |
| 현재 기기에서만 써도 됩니까? | |
| 여러 사람이 같은 데이터를 봐야 합니까? | |
| 변경이 바로바로 보여야 합니까? | |
| 사용자를 구분해야 합니까? | |
| 사용자마다 할 수 있는 일이 다릅니까? | |

<Note>
"예"가 많을수록 좋은 앱이 아닙니다. 오히려 반대입니다. "아니요"가 많으면 빨리 완성되고 관리할 것이 적습니다. 필요해진 다음에 붙이는 것이 항상 낫습니다.
</Note>

## 기획하기

이제 세 가지를 세 줄로 적습니다.

누가 쓰나요. 나 혼자인지, 동료 교사인지, 학생도 쓰는지 구체적으로 적습니다.

무엇을 할 수 있어야 하나요. 동사로 적습니다. 넣는다, 확인한다, 지운다, 알린다 같은 식입니다. 세 개를 넘기지 마세요.

화면에 무엇이 보여야 하나요. 위에서 아래 순서로 적습니다. 화면 하나로 시작하는 것이 좋습니다.

<Warning>
처음 만드는 사람이 가장 자주 하는 실수는 기능을 처음부터 많이 넣는 것입니다. 하고 싶은 것이 다섯 개라면 그중 하나만 골라 먼저 완성하세요. 나머지 넷은 완성한 다음에 붙이면 됩니다.
</Warning>

## Claude에게 요청하기

빈칸을 채워 그대로 보내면 됩니다. 앞에서 적은 답을 옮겨 넣으세요.

<PromptBox>
웹앱을 하나 만들려고 해. 지금은 빈 폴더야.

무엇을 만드나: (한 문장으로)

누가 쓰나: (나 혼자 / 동료 교사 여러 명 / 교사와 학생)

할 수 있어야 하는 것: (세 가지 이내로)

화면에 보여야 하는 것: (위에서 아래 순서로)

데이터 저장: (필요 없음 / 이 기기에만 / 여러 기기에서)

여러 사람이 같은 내용을 봄: (예 / 아니요)

실시간 반영: (예 / 아니요)

로그인: (필요 없음 / 필요함)

사용자 역할 구분: (없음 / 있음)

이번에 넣지 않을 것: (여기에 적은 것은 만들지 마)

먼저 어떤 파일을 만들고 어떤 데이터를 어떤 구조로 저장할지 설명한 다음 작업해 줘.
</PromptBox>

계획이 돌아오면 반드시 읽어 보세요. 내가 "필요 없음"이라고 적은 것이 계획에 들어 있으면 "그건 빼 줘"라고 말한 다음 진행합니다.

기존 앱을 고치는 경우라면 첫 줄을 "현재 앱은 이렇게 동작하고 있어"로 바꾸고 지금 상태를 먼저 설명하세요.

## 실행하고 확인하기

"실행해서 브라우저로 보여 줘"라고 요청합니다.

<Success>
기획에 적은 세 가지 동작이 실제로 됩니다. 화면에 적어 둔 요소가 순서대로 보입니다.

디자인이 마음에 들지 않아도 성공입니다. 보기 좋게 만드는 것은 다음 단계입니다.
</Success>

만든 앱마다 확인할 것이 다릅니다. 아래 항목 중 내 앱에 해당하는 것만 확인하세요.

- 저장이 있는 앱: 새로고침하고, 브라우저를 껐다 켜서 확인합니다.
- 여러 기기용 앱: 휴대폰에서 같은 주소를 열어 확인합니다.
- 실시간 앱: 창 두 개를 나란히 놓고 확인합니다.
- 로그인 앱: 계정 두 개로 서로의 데이터가 보이지 않는지 확인합니다.
- 역할이 있는 앱: 권한이 낮은 계정으로 높은 화면에 접근해 봅니다.

## 수정하기

써 보면서 불편한 점을 하나씩 고칩니다. 한 번에 한 가지만 요청하세요.

<PromptBox>
(불편한 점 한 가지를 구체적으로 적습니다.)

이 부분만 고쳐 줘. 나머지 기능과 디자인은 바꾸지 마.
</PromptBox>

무엇이 불편한지 말로 설명하기 어렵다면 화면을 캡처해서 붙여 넣고 "이 화면에서 이 부분이 불편해"라고 말해도 됩니다.

## 저장하고 공개하기

[GitHub에 프로젝트 올리기](/code/push-to-github)로 보관하고, [내 웹앱 인터넷에 공개하기](/deployment/first-deploy)로 주소를 만듭니다.

데이터베이스나 로그인이 있다면 [Vercel에 환경변수 등록하기](/deployment/environment-variables-on-vercel)까지 해야 합니다. 그리고 배포 전에 [Claude에게 보안 점검 요청하기](/security/ask-claude-for-security-review)를 한 번 실행하세요.

다른 사람이 쓰는 앱이라면 주소를 알려 주기 전에 다른 기기에서 한 번 열어 확인하는 습관을 들이세요.

## 더 해볼 것

- 실제로 일주일 동안 써 봅니다. 이것이 가장 중요한 단계입니다.
- 일주일 뒤에 불편한 점 세 가지를 적고 하나씩 고칩니다.
- 동료에게 보여 주고 무엇이 헷갈리는지 물어봅니다. 만든 사람은 헷갈리는 부분이 보이지 않습니다.
- 처음에 "이번에 넣지 않을 것"에 적었던 기능 중 하나를 이제 붙여 봅니다.
- 필요한 것이 생길 때마다 [더 알아보기](/advanced)에서 해당하는 주제를 찾아 읽습니다.
